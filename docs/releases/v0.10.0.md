## v0.10.0

### 一次创建码优先
- 创建方生成的识别码改为 `P2PF-CREATE-...`。
- 加入方需要返回 NAT candidate 时使用 `P2PF-JOIN-...`。
- IPv6、公开 IPv4，以及可直接穿透的 NAT 场景，加入方会直接建立 QUIC，正常情况下只需交换一次 `P2PF-CREATE` 创建码。
- 只有数秒内无法直接建立连接时，加入方才显示 `P2PF-JOIN` 加入码，用于严格 IPv4 双 NAT 下的双向 hole punching。
- 粘贴错类型的识别码会明确告诉用户当前拿到的是 CREATE 还是 JOIN 码，以及应该在哪一端使用。

### 创建 / 加入命名
- 用户界面统一使用“创建连接 / 加入连接”。
- `status` 显示本机连接角色：创建方或加入方。
- 最终连接超时时提示交换创建 / 加入角色重试。

### IPv6
- IPv6 endpoint 不再运行 NAT punch loop。
- IPv6-DIRECT / IPv6-LAN 成功后，文件数据只走 IPv6 QUIC。
- 程序仍会在建连前探测一次 IPv4 STUN 映射，作为 IPv6 不可用时的 fallback candidate；该 STUN 映射不会参与已选中的 IPv6 数据路径。
- `status` 会把这种映射明确标记为“IPv4 备用，当前 IPv6 链路未使用”。

### 自适应传输重构
旧算法使用单批 QUIC Write 的绝对耗时判断压力，在正常 WAN 或较慢链路上会把 80/200 ms 以上的健康写入误认为拥塞，可能一路退化到 1 lane + 大 pacing。

v0.10 改为吞吐窗口：
- 1~4 data lanes
- 64~256 KiB application chunk
- 周期性向更高档位探测
- 使用实际 bytes/sec 比较探测前后的吞吐
- 高档吞吐没有明显恶化则保留
- 探测导致吞吐显著下降则回退并短暂冷却
- 真正的网络拥塞、丢包、RTT 与 pacing 主体交给 QUIC congestion control
- Windows 从 2 lane / 128 KiB 起步，高档位仅保留 50~100 µs 的轻量 burst pacing，降低 Winsock send queue 峰值
- Linux / macOS 从约 3 lane 起步，健康链路可自动升到 4 lane / 256 KiB

接收端性能会通过 QUIC stream / flow-control backpressure 反映到发送端有效吞吐，因此调节结果同时受网络、接收端磁盘和处理能力影响。

### 对端退出
- 命令行输入现在会周期性检查会话关闭状态。
- 对端退出时，不再要求本机用户额外敲一次键才能发现关闭。
- 收到正常 BYE 后会立即结束行编辑、清理传输与 QUIC/UDP 资源并退出程序。
- 保留 v0.9.1 的 graceful shutdown：正常 QUIC application close code 0 不作为异常输出。

### 协议
- 内部协议与 QUIC ALPN 升级到 v10。
- v0.10 两端需要使用同版本程序。
