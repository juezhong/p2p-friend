## v0.11.0

### 更容易辨认的识别码
- 创建方生成的码改为 `P2PF-INVITE-...`：这是“邀请码”，收到后选择“加入连接”。
- 加入方只有在需要双向 IPv4 NAT 打洞时才生成 `P2PF-REPLY-...`：这是“回传码”，收到后交给创建方。
- 如果把 INVITE / REPLY 粘贴到错误角色，程序会明确说明这个码应该在哪一端使用。
- 保留 v0.10 的“一次邀请码优先、回传码仅 NAT 兜底”流程。

### 紧凑二进制信令
- 识别码 payload 从 Base64(JSON) 改为 Base64(紧凑二进制)。
- IPv4 candidate 直接保存 4-byte IP + 2-byte port。
- IPv6 candidate 直接保存 16-byte IP + 2-byte port。
- 地址族与 candidate 类型压缩到 flags。
- 不再在每个识别码里重复保存 JSON 字段名和 IP 字符串。
- 相同 IP:port 的重复 candidate 自动合并；同一 endpoint 同时为 host / srflx 时优先保留 host。
- loopback、link-local、unspecified 等明显不可用地址不会编码进识别码。
- candidate 数量有上限，避免异常输入生成超大识别码。

### 安全性不缩水
- 会话 token 仍然完整保留 256 bit。
- INVITE 中仍然完整保留 SHA-256 临时证书指纹。
- 缩短长度来自编码方式与去重，不通过截短认证信息实现。

### 兼容性
- 信令格式、内部协议与 QUIC ALPN 升级到 v11。
- v0.11 两端需要使用同版本客户端。
- 文件传输、QUIC 多 stream、自适应带宽、NAT punching、单传输仲裁和 graceful shutdown 逻辑保持不变。
