## v0.11.1

### Deterministic two-code handshake
- Remove the v0.10/v0.11 user-flow heuristic that first waited several seconds trying an INVITE-only connection before deciding whether to display a REPLY code.
- Connection setup now always exchanges the compact `P2PF-INVITE-...` and `P2PF-REPLY-...` codes before starting the real QUIC connection.
- The creator does not start the real QUIC listener / connectivity flow until the REPLY code has been pasted and validated.
- The joiner generates REPLY immediately after reading INVITE, then silently waits for the creator to paste it.
- This removes the UI race where the REPLY prompt / waiting text could remain visible until another Enter key press.

### Path selection after candidate exchange
- Both peers have the complete candidate sets before connection selection begins.
- Globally routable IPv6 candidates get a short head start so dual-stack peers normally select `IPv6-DIRECT`.
- IPv4 candidates remain an automatic fallback when IPv6 is filtered or unreachable.
- IPv4 NAT punching uses the already-exchanged STUN / host candidates; no additional manual signaling is required.

### Signal codes
- Keep the compact v0.11 binary code format.
- `P2PF-INVITE-...` remains the code generated by the creator and sent to the joiner.
- `P2PF-REPLY-...` remains the code generated by the joiner and returned to the creator.
- The wire protocol and code encoding stay compatible with v0.11.0; this release changes the interactive connection state machine.
