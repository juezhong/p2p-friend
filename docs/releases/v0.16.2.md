## v0.16.2

### 全链路自适应吞吐

- v0.16.1 的 64 MiB LAN 批次等待进一步改成累计 ACK 驱动的滑动飞行窗口，不再每个窗口发送完后全局停等。
- Linux LAN 从 64 MiB flight window 起步，健康时自动探测 128 MiB、256 MiB；连续退化或失败才回退。
- 非 LAN 链路也使用同一套自适应逻辑：从较小窗口起步，稳定时逐步扩大，最高 128 MiB。
- Windows 继续保留更保守的初始值和队列上限，但同样能够自动升 lane / chunk / flight window，不再是固定保守模式。
- 发送端只保留未累计 ACK 的 chunk，ACK 前直接复用最终 resilient frame buffer；重传复用同一 buffer，不重复 make/copy。
- 数据生产、SHA-256、QUIC worker 并行流水；所有 data lanes 可持续被喂满，同时用 ACK window 限制总内存。

### 更大的发送工作队列

- Linux LAN：最多 32 chunk/lane 的 producer queue（4 lane 时 128 chunk）。
- Linux/macOS 非 LAN：最多 8 chunk/lane。
- Windows：最多 4 chunk/lane，避免 Winsock UDP burst 重新引入不稳定。
- `status` 现在显示真实 queue 和当前自适应 flight window，不再使用旧的固定 2 chunk/lane 公式。

### 会话建立延迟

- 主 QUIC 完成认证后立即进入 control session；4 条 data-only QUIC 改为后台并行建立。
- 文件传输只要求至少一条 data lane 可用即可开始，其余 lane 建好后自动热加入。
- 初始远端 `pwd` RPC 最多只占用 50 ms 前台预算，超过后转后台完成，不再阻塞命令行出现。
- 因此 LAN 和 WAN 都不再为了“先凑齐 4 条数据连接”而延迟进入 shell。

### 稳定性保持

- 主 QUIC 仍然 control-only。
- data-only QUIC 仍可独立失败、移除、重建。
- 累计 ACK、file ID、防迟到 chunk 污染、未确认数据自动重传全部保留。
- 自适应扩窗有 256 MiB（LAN）/ 128 MiB（非 LAN）硬上限，不会无限堆内存。

### 验证

- Linux sustained resilient LAN transfer 通过。
- Windows sustained QUIC transfer 通过。
- 两个平台的长传测试仍包含传输中主动关闭一条 data-only QUIC，并验证自动恢复、SHA-256 正确、control session 继续可用。
- `go test ./...`、`go test -race ./...`、`go vet ./...` 以及 Linux/Windows/macOS 构建全部通过。
